# Package R1: the image library `sharp` removed from the TypeScript template

| | |
| --- | --- |
| Date | 12 November 2026 |
| Why | The template carried packages of `sharp` under LGPL, outside the permitted list (known gap 40). Asked whether to remove it, approve it by name, or give up the stack, the owner answered "REMOVE IT" (`docs/DECISIONS.md`) |
| Package | R1 of `docs/BUILD-PLAN.md`: "Remove or replace the named packages and change only what directly uses them. Nothing else is touched" |
| Run on | The development machine (a cloud session). The install, type check, build and licence listings ran directly on the host in `templates/next/`. The demonstration built and ran the template in containers on the development profile, which shares the host's network; as before, creating the tables and sample users ran from the host (known gap 29) |
| Done means (plan) | (1) "The named packages no longer appear in the component's dependency list." (2) "The licence check under the single rule of 0.4 passes for that component." (3) "The component's existing tests pass with the replacement" |
| Result | (1) **Shown.** (2) **Not met:** the single rule of package 0.4 does not exist for the template, and the template's committed check still refuses `caniuse-lite`, which the owner approved but which is not entered in that check; as committed that check also skips every package whose name begins with `@` (known gap 43). (3) **Not shown as worded:** the template has no automated tests. In their place the type check, the build and the template's demonstration run were repeated and passed; whether that may stand in for "existing tests pass" is the owner's to say. **State: built, not tested. Not for merging** until (2) is met, which waits on the owner's answer in `docs/STATUS.md` |

## What was changed, and only this

| File in `templates/next/` | Change |
| --- | --- |
| `vendor/no-sharp/` | New: an empty stand-in of this template's own, named `sharp`, marked private and unlicensed. Loading it raises an error that says why |
| `package.json` | `sharp` is listed as a dependency pointing at the stand-in, and an `overrides` entry makes Next.js use the same one instead of the real library |
| `package-lock.json` | Regenerated by `npm install`. The real `sharp` and everything it brought are gone. One other entry changed a flag and nothing else (list below) |
| `next.config.ts` | Next.js's image optimiser turned off: its route answers "not found" and images are served as they are |
| `Dockerfile` | Copies `vendor/` before installing, so the container build finds the stand-in |
| `README.md` | A section saying that `sharp` is not installed, why, and that it must not be added back without the owner's approval |

Nothing in the template used `sharp` or Next.js's image component.

**What behaves differently without `sharp`,** as an independent reviewer found by trying each on a copy of the template: the image optimiser route answers "not found"; Open Graph image generation still looks for `sharp`, does not find it and falls back to its built-in renderer; a statically imported image file works with the default bundler, which the template's build uses, and fails the build under the older webpack bundler. Apps built from the template get no automatic image resizing.

**Tried first and rejected:** an `overrides` entry alone, without listing the stand-in as a dependency. With `"sharp": "file:./vendor/no-sharp"` the install succeeded but left a link pointing at a folder that does not exist (the path was taken from inside Next.js's own folder). With `"sharp": "file:../../vendor/no-sharp"` the install worked, but a clean install from the lock file (`npm ci`, which the container build uses) stopped with "Missing: sharp@0.0.0-removed from lock file". Listing the stand-in as a dependency and pointing the override at that entry (`"$sharp"`, a form npm documents) makes both `npm install` and `npm ci` work.

## What this does not show

- That the licence check passes: it does not yet (see the result above).
- Anything about another machine: the packages installed depend on the machine, though the lock file, which covers all machines, now lists no `sharp` or `@img` package from the registry.
- That an app generated from the template will never need image processing. If one does, it cannot use `sharp` without the owner's approval.
- That `sharp` cannot come back: nothing checks for it yet (known gap 44).
- Whether any licence is complied with. Nothing here says so.
