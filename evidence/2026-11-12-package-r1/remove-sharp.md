## What was changed, and only this

| File in `templates/next/` | Change |
| --- | --- |
| `vendor/no-sharp/` | New: an empty stand-in of this template's own, named `sharp`, marked private and unlicensed. Loading it raises an error that says why |
| `package.json` | `sharp` is listed as a dependency pointing at the stand-in, and an `overrides` entry makes Next.js use the same one instead of the real library |
| `package-lock.json` | Regenerated by `npm install`. The real `sharp` and everything it brought are gone. One other entry changed a flag and nothing else (list below) |
| `next.config.ts` | Next.js's image optimiser turned off: its route answers "not found" and images are served as they are |
| `Dockerfile` | Copies `vendor/` before installing, so the container build finds the stand-in |
| `scripts/check-licences.sh` | The approved name `caniuse-lite` entered in the list of exceptions with its version (`caniuse-lite@1.0.30001823`), with the date and where the approval is recorded. That list is no longer empty, so the tool no longer skips packages whose names begin with `@` (known gap 43). This goes beyond "nothing else is touched"; it is the choice of 12 November |
| `scripts/check-lock.mjs` | New, and run by the licence check: it fails if the lock file lists a registry `sharp`, any `@img` package or an unexpected local package, or if `caniuse-lite`'s recorded licence is no longer CC-BY-4.0. **This also goes beyond R1's scope** ("nothing else is touched") and was not one of the three options put to the owner; it was added by Claude Code to answer a review finding, is recorded in `docs/DECISIONS.md`, and is listed for the owner to confirm |
| `README.md` | A section saying that `sharp` is not installed, why, and that it must not be added back without the owner's approval |

Nothing in the template used `sharp` or Next.js's image component.

**What behaves differently without `sharp`,** as an independent reviewer found by trying each on a copy of the template: the image optimiser route answers "not found"; Open Graph image generation still looks for `sharp`, does not find it and falls back to its built-in renderer; a statically imported image file works with the default bundler, which the template's build uses, and fails the build under the older webpack bundler. Apps built from the template get no automatic image resizing.

**Tried first and rejected:** an `overrides` entry alone, without listing the stand-in as a dependency. Both forms were run again on 12 November from the same start: the template's `package.json` and lock file as they were before this change, plus the `vendor/` folder, in an empty folder with nothing installed. With `"sharp": "file:./vendor/no-sharp"` the install succeeded but left a link pointing at a folder that does not exist (the path was taken from inside Next.js's own folder). With `"sharp": "file:../../vendor/no-sharp"` the install worked, but a clean install from the lock file (`npm ci`, which the container build uses) stopped with "Missing: sharp@0.0.0-removed from lock file". Listing the stand-in as a dependency and pointing the override at that entry (`"$sharp"`, a form npm documents) makes both `npm install` and `npm ci` work.
