# Package R1: the image library `sharp` removed from the TypeScript template

| | |
| --- | --- |
| Date | 12 November 2026 |
| Why | The template carried packages of `sharp` under LGPL, outside the permitted list (known gap 40). Asked whether to remove it, approve it by name, or give up the stack, the owner answered "REMOVE IT" (`docs/DECISIONS.md`) |
| Package | R1 of `docs/BUILD-PLAN.md`: "Remove or replace the named packages and change only what directly uses them. Nothing else is touched" |
| Run on | The development machine (a cloud session). The install, type check, build and licence listings ran directly on the host in `templates/next/`. The demonstration built and ran the template in containers on the development profile, which shares the host's network; as before, creating the tables and sample users ran from the host (known gap 29) |
| Done means (plan) | (1) "The named packages no longer appear in the component's dependency list." (2) "The licence check under the single rule of 0.4 passes for that component." (3) "The component's existing tests pass with the replacement" |
| Result | (1) **Shown.** (2) **Not met:** the single rule of package 0.4 does not exist for the template, and the template's committed check still refuses `caniuse-lite`, which the owner approved but which is not entered in that check. (3) The template has no automated tests; its existing demonstration run was repeated and gave the same seven screenshots' worth of results. **State: built, not tested. Not for merging until (2) is met**, which waits on the owner's answer about how a licence code becomes true (`docs/STATUS.md`, question 1) |

## What was changed, and only this

| File in `templates/next/` | Change |
| --- | --- |
| `vendor/no-sharp/` | New: an empty stand-in of this template's own, named `sharp`. Loading it raises an error that says why |
| `package.json` | `sharp` is listed as a dependency pointing at the stand-in, and an `overrides` entry makes Next.js use the same one instead of the real library |
| `package-lock.json` | Regenerated by `npm install`. The real `sharp` and everything it brought are gone; nothing else changed (list below) |
| `next.config.ts` | Image optimisation turned off, so Next.js never tries to load `sharp` |
| `Dockerfile` | Copies `vendor/` before installing, so the container build finds the stand-in |
| `README.md` | A section saying that `sharp` is not installed, why, and that it must not be added back without the owner's approval |

Nothing in the template used `sharp` or Next.js's image component.

**Tried first and rejected:** pointing only the `overrides` entry at the stand-in. That removed the packages, but a clean install from the lock file (`npm ci`, which the container build uses) then failed as out of step. Listing the stand-in as a dependency as well makes both `npm install` and `npm ci` work.

## What this does not show

- That the licence check passes: it does not yet (see the result above).
- Anything about another machine: the packages installed depend on the machine, though the lock file, which covers all machines, now lists no `sharp` or `@img` package from the registry.
- That an app generated from the template will never need image processing. If one does, it cannot use `sharp` without the owner's approval.
- Whether any licence is complied with. Nothing here says so.
