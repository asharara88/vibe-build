# Package 0.6c, first step: the design's assumptions, measured

Measured by Claude Code on 13 Nov 2026 on this cloud session's machine (Docker 29.9.2, Compose 5.6.1), in two sittings. The first sitting's last output is at 10:21 UTC; the measurement containers stopped with a restart of the session's container at about 10:40 UTC; the second sitting continued at 10:44 UTC. The owner chose option (a), private networks, on 13 Nov 2026 (`docs/DECISIONS.md` on package 1.5's branch).

- Inputs: the design draft and its independent critique (not in the repository; the critique's list "To measure before building", items 1 to 9, and the draft's risks 1, 2 and 4 are the rows below).
- How: small throwaway Compose projects and `docker` commands. Every object was named `m06c-...` and every one was removed at the end (`measure/00-...`, `measure/10-...` and `measure/99-...` list them before and after).
- Images: only images already on the machine: the approved `node:22-alpine` and `postgres:16-alpine`, and the acceptance runner's image as package 3.1 builds it. Nothing new was pulled.
- No model was called; the gateway was a stand-in that answers with its own name. Nothing a model wrote was run. The data is made up (the template's sample users).
- The machine's firewall, routes, system settings and Docker settings were not changed.
- Raw outputs are in `measure/`, the throwaway files in `measure/files/`. The checkout's path is written `<checkout>`, the scratch folder's `<scratch>`. The session proxy is named by host and port only.

Words used below:
- **bridge**: a private network Docker makes on the machine.
- **internal**: Docker's setting for a bridge with no way out to the internet.
- **"isolated" mode**: Docker's option that also gives the machine no address on that bridge.
- **relay**: option (a)'s small forwarder on the machine.
- **door**: option (a′)'s forwarder inside the project's network, which hands connections to the builder's proxy through a file-like socket on the machine.

Whatever forwards to it reads the port when it starts. It must be restarted when the session changes, and fail closed in between (row 8).
- **Routes.** Every container reports packet forwarding on. With every capability dropped, a container could not change its routes; with the network-admin capability given back, it could (`02e`). Keep dropping every capability, with its test.
- **Both forwarders keep a direct way out.** In each option, the builder's own forwarder still has a route to the internet: the egress container in (a), the machine-side proxy in (a′). Only its code keeps it to the session proxy, which is why row 8's change matters.

## The door: (a′) chosen, and why

Both doors worked. Option (a′), the Unix-socket door, is chosen for what was measured:
1. **No route out in the project's network.** No container on the project's networks has a route out or an address on the machine. The door's rows are all "no route" or "no answer" (`probes-b`). In (a), the egress container on `ext` reached the internet directly, resolved outside names, and reached the machine's open port 2024 (`probes-a`).
2. **No listener on a machine address.** In (a), the relay's ports were reachable from every ordinary bridge, and only the source check refused them. Without the check, they handed out the session proxy (github.com included) and the gateway (`probes-relay-check-off`). In (a′), the only new listener is on 127.0.0.1, which bridges cannot reach (`probes-b`).
3. **Who may connect is set by the socket's file permissions:** uid 1000 yes, uid 1001 no (`09c`).
4. **No subnet to choose,** so no risk of an overlap with the machine's own network (`06a`).
5. **It survives a restart and serves the build:** the machine side restarted with no change at the door, and the build reached the registry through the loopback port (`09c`, `09d`).

What it costs, each to be built and shown:
- a socket folder per project on the machine;
- one socket per kind of client, because the proxy no longer tells clients apart by address;
- a small forwarder in the door (new code);
- untried on Docker Desktop for Mac, which is not where the builder runs.

It stays within the owner's option (a). Project containers sit on private networks with no route to the machine. The builder's proxy is their only way out, and it reaches the internet only through the session's proxy and the gateway.

## Design changes the measurements call for

1. All project networks use `internal: true`, the "isolated" option and `enable_ipv6: false`, with no gateway address set. Nothing assumes `.1` is the machine.
2. The door is (a′): no `ext` network and no relay.
   - On the machine: the builder's egress proxy listens only on Unix sockets in a per-project folder (uid 1000, mode 750) and on a 127.0.0.1 port for the image build. A socket forwarder leads to the gateway's loopback port.
   - In the project: a door container on `out`, named `egress`, with read-only roots.
3. The gateway gets a fixed port, `egress:4010`, and the engine uses `ANTHROPIC_BASE_URL=http://egress:4010` (with `NO_PROXY=egress` if proxy settings are given). No `gateway.internal`; no per-host route in the egress proxy. Package 2.2 shows the Agent SDK's own client.
4. Each client gets its own list, on its own socket or port: the engine, the gateway and the registry only if 2.2 needs it; the build, the registry only. The tools container is on `data` only: it created the tables and users that way.
5. The egress proxy fails closed. It refuses to start without a valid upstream, and answers 502 when the upstream closes before a tunnel is set up.
6. The image build:
   - `npm ci --ignore-scripts`, through the builder's proxy, with no certificate copy;
   - the guard check and `next build` under `RUN --network=none`;
   - `vendor/` added to the protected paths;
   - no `# syntax=` line.
7. The database is reached as `db:5432`, with no port on the machine. Both health checks run over TCP (`pg_isready -h 127.0.0.1`).
8. The runner is on `front` only, with `BASE_URL` = `APP_URL` = `http://app:<port>`.
   - The "right app answers" check runs in a short-lived container on `front`.
   - The screenshot and demo scripts stop reaching the app or the database from the machine.
   - A new known gap: pages that need a secure context.
9. The probe reads every machine address and port, records who answered, and runs with comparison containers, both misconfigurations and 64 lookup threads. Its expected lists include the app as seen from `data`, or the app listens on `front` only.
10. Every capability stays dropped, with its test. The machine-side proxy reads the session proxy's port when it starts and is restarted with the session.
