# Package 3.1: acceptance store and runner (design)

**Draft, parked on the owner's questions 11 and 12 (13 Nov 2026); not approved; nothing built.**

**For the owner, in five lines.**
1. **What would be built:** a separate place, outside every project's folder, where the builder keeps each version of a project's acceptance tests and refuses to rewrite one (the refusal is the builder's own code only: the builder runs as *root*, with full rights on this machine, which file settings do not stop); a separate box (a *container*) that runs those tests in a browser against the running app; and attempts, from the box that writes the app's code, to reach the tests by file path, network, database and history, each recorded with its result. They would show what that box reached as it is built; it is the scripted engine's box, which has no network at all, so they would say nothing about the real engine's box (package 2.2), which needs a route to the gateway.
2. **What you would see:** a screenshot of acceptance item 1 passing; a deliberately broken copy of the app failing, with the item and the step named; a run that did not happen reported as "did not run"; and a table of attempts, from the engine's box, to reach the tests, each with its result.
3. **What needs you:** question 11, the licences of the browser and of the container images; question 12, whether tests written in advance by Claude Code may stand in until a model writes them, with the change to decision E that goes with it (section 9) (`docs/STATUS.md`, "Waiting on the owner").
4. **Until you answer:** nothing of 3.1 is built. W1 and W2 wait on question 11 too (W1's browser run; W2's sandboxes, which run the images it asks about); package W3, which needs no container and no browser, is taken instead.
5. **What it would not show:** tests written by a model, acceptance items 2 to 6, the server profile, or anything about the real engine (package 2.2).

**Tags.** **read**: read in the file named, at commit `61640f4`. **measured**: run on the development machine on 13 Nov 2026; the outputs are in the session's scratch folder, not in the repository, and the package's own run repeats them with the exact commands. **proposed**: a choice this design makes. **inferred**: not checked.

**Words.** A *mount* puts a folder of the machine inside a container. A *manifest* lists a version's files with their fingerprints (SHA-256). A *marker* is a random string put in every test file of a version, so a search finds any copy. A *trace* is Playwright's recording of a run. A *base image* is the starting state a container image is built from. An *exit code* is the number a program ends with. The *development profile* is how projects run on the development machine, and a *sandbox* is one project's set of containers there. *LGPL*, *MPL* and *GPL* are licences that carry duties when the software is passed on, the GPL's the strongest. A *fingerprint* (here SHA-256) is a value worked out from a file's bytes; any change to the file changes it. A *tag* such as `node:22-alpine` names whatever image was last published under it; a *digest* is the fingerprint of one exact image. The *headless shell* is a build of the browser with no window, for automated use. A *Compose service* is one container in the file Docker Compose starts a project from; a Compose *profile* is a named group of services started only when asked for. *Hardening* is the set of limits every project container gets (manager.ts:92-98). A *link* is a file that points to another path; `lstat` reads a link itself without following it. A *fixture* is a piece of set-up Playwright hands to each test; an *attachment* is a file a test adds to its results. The *acceptance writer* is the builder's part that is to ask a model to write the tests (design note 2.7), and a *generation log* the record of what that call was given and returned. Other words, such as container, container image, Playwright and stand-in, are in `docs/STATUS.md`, "Words used here".

## 1. The store (proposed)

- A new setting, `BUILDER_DATA_DIR`, with no default inside the checkout. The store is `$BUILDER_DATA_DIR/acceptance/<projectId>/`. The project id is checked before it is used as a folder name.
- The store's code refuses a root inside the repository, `builder/`, `templates/` or a sandbox folder, compared after resolving links (realpath). Why (read): the engine mounts `builder/scripted` (manager.ts:173); the egress container mounts all of `builder/` (:253, :303); the template is copied into the workspace (demo-scripted.ts:49); the history is `<sandbox>/workspace.git` (project-repo.ts:2-6); a sandbox folder is deleted after a run (demo-scripted.ts:248).
- Versions `v001`, `v002` and so on, each written under a temporary name and then renamed; a version that exists is refused. Each holds `manifest.json`: who wrote it, the app spec's fingerprint, each item's number, file and fingerprint, and the version's marker. **Every test file also carries the marker** in its label line.
- **Versions are protected by the store's code only.** Read-only file modes do not stop root, and the builder runs as root here (read: known gap 57; demo-scripted.ts:91-94). So the runner checks each file against the manifest before any test starts, the builder checks the manifest against its `acceptance.version.written` event, and the records say "the store refuses a rewrite", never "cannot be changed".
- Inferred: a mount of one project's folder still works under a store root of mode 0700, because Docker mounts as root. Measured first.

## 2. Who writes the tests in 3.1 (question 12)

- **Option (a):** a plain function copies fixed tests from `stand-in-acceptance/example-1/`, a top-level folder that no container mounts (read: manager.ts:173, :253, :303). Every file starts: "Stand-in acceptance test, written in advance by Claude Code (the AI assistant building this project), not by the builder's acceptance writer. No model call by the builder." The short label "stand-in test" is in every test title, every acceptance event (`written_by: "stand-in"`), and every screenshot and evidence file name. "Scripted" stays the label of the fixed app changes (`docs/DECISIONS.md`, 12 Nov, "Package 2.1, the 'scripted' label"). The folder is committed, so the tests' text is in the builder repository's history before any export (amendment :198, section 9).
- **Option (b):** the same text reaches the store through the writer's own path: a call through the gateway to a stand-in provider that replays it, as W3 does (BUILD-PLAN.md:233), so a generation log is shown, against a stand-in only.
- **Either way, disclosed:** one author, Claude Code, wrote both the scripted app's changes and the test, and the test was written knowing the app. For example it finds the request by its reason, which the app lists (my-requests/page.tsx:67-71) and the spec's screen does not ask for (example-1-leave-request.json:44). It shows the separation of the tests' files from the engine, not independent acceptance. Question 12's option (a) says both.

## 3. The runner (proposed, on measured ground)

- **Image: route B.** `ubuntu:24.04` with Node 22's program copied from `node:22-bookworm-slim`, Ubuntu's libraries added by `playwright install-deps` (fixed by name only, at the versions Ubuntu 24.04 serves on the day of the build; each build's package list with versions is recorded and shown to the owner when it changes), and Chrome for Testing's headless shell 153.0.8010.12 from `storage.googleapis.com`, its zip's SHA-256 pinned; both base images pinned by digest (`docs/SOURCES.md`, 13 Nov). Measured: it built in 43.6 s and ran Playwright Test with no network as a non-root user, one test passing and one failing by name; its browser program is byte-identical to the official image's copy. Reported by the measuring agent but not in its files: the hardening flags, the image's 1.22 GB, and that no certificate or proxy setting was left in it.
- **Why not route A**, the official image `mcr.microsoft.com/playwright:v1.63.0-noble` (pulled in 28 s, measured): it also carries Firefox, WebKit and Node 24. Route B carries one browser and Node 22, so fewer licences to approve. Playwright's own download host and Debian's and Alpine's mirrors are refused by the session's proxy (measured), so the browser comes from Google's Chrome for Testing address.
- Built once per builder from `builder/runner/Dockerfile`, with its own package list and lock file (`@playwright/test` 1.63.0, Apache-2.0, read on npm 13 Nov). The licence check gains `builder/runner/` as a third component, with its own copy of the rule and its test (`docs/DECISIONS.md`, package 0.4). The session certificate is copied into the build context, git-ignored, used only by `RUN --mount`, and made conditional off the cloud session, as `templates/next/Dockerfile:16` does.
- A Compose service `acceptance` under its own profile, added to `ONE_OFF_PROFILES` and refused by `up` like tools and engine (read: manager.ts:462-477, :633-645), run through `runStreaming`, present only while checks run (design note 2.5). The common hardening (manager.ts:92-98), a 512 MB `/tmp`, a non-root user, no settings file, and only `BASE_URL` and `RUN_ID`. Not measured with Chromium: the 256-process and 1 GB limits (the measured runs used 2 GB); raising one is recorded as a change.
- **What it sees:** `/acceptance`, the version, read-only; `/results`, a fresh run folder (refused if it exists), handed to the runner's user as in gap 57; `/run/secrets/sample-password`, one file the runner's user can read (sandbox secrets are written 0600: manager.ts:371-377). No workspace, key or database settings.
- **Network.** Development profile: `network_mode: host`, `BASE_URL` equal to the app's `APP_URL`, the only origin the sign-in library trusts (read: templates/next/src/auth.ts:19-20). Given no database settings, it can still open a connection to the builder's database and the project's on this profile (gap 60). Server profile: the project's internal network; designed, not shown.
- **Not measured, so measured first in the package (inferred):** a test file under `/acceptance` loading `@playwright/test` from `/runner/node_modules` (Node looks from the file's own folder); TypeScript test files; reading the password file; the host network against the real app with sign-in.

## 4. Reading the result (proposed)

- The builder's own configuration, baked into the image: retries 0, workers 1, `forbidOnly`, trace and screenshot on, the JSON and line reporters, and `metadata` holding the run id and the manifest's fingerprint. It is not taken from the test folder, but it is no defence against a test written to cheat: a test file can call `test.describe.configure` (read: playwright/lib/common/index.js:2321-2329) or `test.fail()`, and its code can write to `/results`.
- Every item in the manifest starts as **did not run**. It is **passed** only if: the right app answered before the start (section 5); the container exited 0 or 1 within its time limit; `results.json` was read under the rules below and parses; its metadata holds this run's id and this version's fingerprint; the item's test appears once, in the manifest's file for that item; it has `expectedStatus` "passed", outcome "expected", exactly one result, retry 0, status "passed", and no skip, fixme or fail annotation (read: playwright/lib/runner/index.js:4182-4198); and its screenshot exists.
- **Failed** needs a recorded failure, with the step named, or "no step named" for a failure outside a step or a test's own time limit. Everything else stays did not run: a kill, exit code 137, the overall time limit, a skipped or interrupted test, a missing file. The run reads "version passed; checklist incomplete" while items 2 to 6 have no test (gap 54).
- **The builder reads the run folder without following links:** lstat only, regular files only, inside the run folder, with size limits; attachment paths outside `/results` are ignored. The runner can write links there and the builder runs as root (same class as gap 51).
- **Events**, written by the builder after the container exits: `acceptance.run.started`, `acceptance.item`, `acceptance.run.finished`, each with the run id, the version, its fingerprint and `written_by`; a `projects` row first (read: 001_init.sql:24).
- **What test text reaches the records:** the event log gets each item's number, its step title (test text) and its result. Playwright's error message carries lines of the test's source (read: formatError, playwright/lib/runner/index.js:1489-1502; seen in the measured output), so it stays in the run folder and the event holds its path and fingerprint; the log is append-only. The project's database holds the dates, days and reason the test typed, by design.
- The per-run password may be in the trace, `results.json` or error files (inferred). They stay in the run folder, listed by fingerprint, and `evidence/` is searched for the password before it is committed (hard rule 3).

## 5. The fixed test, the broken copy, and the wrong-app risk

- **Item 1** follows map 3: sign in as `employee@example.test`; My requests, then New leave request; 2027-05-03 to 2027-05-07 (a Monday to a Friday) and 5 days, with a reason unique to the run; Submit. Then, inside the list item and not the banner, which says "Waiting" whatever was stored (read: my-requests/page.tsx:46-50): status `/waiting/i`, none of approved, rejected or withdrawn; a full-page screenshot. Each step is a `test.step`.
- **The broken copy:** change set `03-wrong-status` replaces `actions.ts`, changing `status: "waiting"` (read: actions.ts:24) to `"approved"` (allowed: app-schema.ts:40), and both message files, so the banner adds "deliberately broken copy" to the scripted label. It is kept outside `builder/scripted`, which every engine container mounts whole (manager.ts:173), and given to the engine container for step 03 of the broken run only (how is settled when built); the folder-listing test (scripted-engine.test.ts:152-159) is extended to cover it. The npm tests are extended, never weakened: fingerprints and labels, the manifest helper's chaining (scripts/scripted-manifest.ts:23-32, the previous fingerprint at :29); example 1 stays at two steps (scripted-engine.test.ts:74-77).
- **Wrong app.** On the development profile the app's health check asks `127.0.0.1:<port>` (manager.ts:193-198, :274), so any program on that port satisfies it, and Compose project names come from the project id (:100-102). So the broken copy runs **after the passing sandbox is destroyed**, under the same project id, in a fresh sandbox and database (template, 01, 02, then 03, each committed `[scripted]`); before each `up` the builder checks that nothing listens on the app's port; both runs use **the same store version** (same fingerprint). Each sandbox has its own made-up password (demo-scripted.ts:54), so a run against another app would fail at sign-in (inferred).
- Expected: the broken run fails at item 1, step "sees status waiting", expected `/waiting/i`, received the list item's whole text, which contains "Approved"; its screenshot shows the "deliberately broken copy" banner; the step-02 tree is the same in both histories (`git rev-parse HEAD~1^{tree}`).

## 6. Done means (4): attempts from the engine container, and its mounts

- **The version is written before step 01 runs.** Design note 2.7:193 has the checklist written "before any code exists"; writing the test version before step 01 extends that to the tests, so the separation covers the build steps, not only a probe afterwards.
- **The mount rule is enforced in `runStreaming` for the engine service**, where the per-run mounts are added (read: manager.ts:509-510, :534-541; scripted.ts:247): a source inside the data directory, equal to it or above it is refused, both sides resolved with realpath. A test of the Compose document alone cannot see those mounts.
- **Mounts listed:** each real step container (01, 02, and 03 in the broken run) by `docker inspect` while it runs, kept alive by `delayMsPerWrite` (scripted.ts:115-116), with its exact `docker compose run` arguments; the evidence fails if an inspect did not finish before its container ended (no fixed wait). Plus an unfiltered `/proc/self/mountinfo` from inside (2.1's listing was filtered: demo-scripted.ts:150-151), and the runner's own mounts the same way (design note 7.2:515).
- **By file path:** a probe, mounted read-only at `/probe` as 0.6a's is (demo-isolation.ts:91-96), opens by their host paths the store root, the project folder, the version, a test file, the run folder, the repository's `stand-in-acceptance/` and `evidence/`, and `/acceptance` and `/results`. The marker is searched for from the host in the source of each of the engine's mounts; inside, the probe gets it in two halves joined only in memory, so the whole string is never in its arguments or in `docker inspect` (0.6a passes its settings as arguments: demo-isolation.ts:91). It also searches for a phrase of the test's source and the run's reason.
- **Over the network:** 0.6a's `isolation-probe.mjs`, unchanged. Its C5 and C7 aim at 127.0.0.1, which in this container is its own loopback (isolation-probe.mjs:255, :257), and are marked so, as 0.6a's table does. Beside every network result: "scripted engine container, no network at all (gap 50); says nothing about 2.2".
- **Through the project's database:** this container has no route to it. From the host, dumps of the project's database and of the builder's events are searched for the marker and the phrase: expected 0, while the request the test typed is there by design, and the evidence says so.
- **Through the project's history:** inside, `/workspace/.git` and the history folder are absent; on the host, `git log --all --name-only` shows no acceptance file and a search of every revision for the marker finds nothing.

## 7. What package 3.2 is handed

- The test text names no runner path or address: the base URL comes through Playwright's `use.baseURL` from a setting, the sample password through a setting read by a fixture, screenshots through Playwright's attachments. So the same files can run from the exported copy (BUILD-PLAN.md:187) without being edited (2.7:197).
- The exporter commits into a separate export repository, never into `<sandbox>/workspace.git`, so later change steps do not have the tests in their history. Proposed: it copies the version the last passing run used, named by its id. The template has no `@playwright/test` today (templates/next/package.json); that, whether a customer's copy may hold a browser, and any database image the export's start file names (today the sandbox uses `postgres:16-alpine`), are 3.2's (question 11 says they are asked again then).

## 10. For an engineer

- On the development profile the runner shares the machine's network and can open connections to both databases (gap 60): whether that is acceptable is an engineer's judgement. The change to what the runner sees and who writes its results (section 9, :196) is the owner's, in question 12.
- Playwright 1.63.0 starts Chromium with `--no-sandbox` unless `chromiumSandbox: true` is given (read: playwright-core/lib/coreBundle.js:43346-43347; seen in the measured runner's launch log). From 2.2 on, page code a model wrote would run with the browser's sandbox off, in the container that holds `/acceptance` and `/results`. Gap 55's sentence about the host is corrected on this ground.
- The password inside traces and run files; versions protected by code only while the builder runs as root (gap 57). Each goes into `docs/KNOWN-GAPS.md` when the package takes it.

## 12. From the two critiques: not taken, and why

- **Building the store, runner and probes now and marking the package later** (first critique, point 4), or listing what may be built meanwhile (second, 1c): not taken. Plan section 3, step 4 parks the package and takes the next; question 12's option (b) would change how the store is written. W1 and W2 wait on question 11 too; W3 is taken.
- **Applying step 03 in the passing sandbox** (second, 8b): not taken, as a preference. In the same sandbox the broken run's list, and so its screenshot, would also show the passing run's "Waiting" request beside the broken run's "Approved" one, which makes the screenshot harder to read; a fresh sandbox shows the broken run's request alone. The cost is a second sandbox and database, recorded in the free disk before and after.
- **A marker prefix assembled at run time** (first, 1): taken in another form (section 6). The draft's "294 components" is dropped: how it was counted is not recorded (second, 4e). Every other correction of both critiques was checked against the repository and is taken above, including the four wrong citations (auth.ts:19-20, actions.ts:24, scripted-engine.test.ts:152-159, scripted-manifest.ts:29).
