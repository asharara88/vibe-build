# Environment check (Task 0, item 1)

Measured on 11 November 2026 inside a Claude Code cloud session. Everything here was run, not assumed. Re-run before relying on it: the documentation says these resources are approximate and may change.

## Plain-language result

- **Can it run a container?** Yes. The Docker daemon is not running when a session starts; it starts with one command and then works. *Not always, as seen on 12 and 13 November 2026: on 12 Nov that command failed until Docker's start script was patched, and on 13 Nov it failed once until a file left from the day before was deleted (last section).*
- **Can a container reach the package registry?** Yes, with a workaround. As first written on 11 November: "On Docker's default network a container has no internet at all, because this machine reaches the internet only through a local proxy that listens on the machine itself." *Corrected by measurement on 12 November 2026 (package 0.6a, `evidence/2026-11-12-package-0.6a/isolation-checks.md`): neither half holds as written.* A container on Docker's default network, with no proxy setting and no certificate, got answers on port 80 (A2, A5) and to name lookups (D1, D5); its HTTPS request to the registry got a certificate it did not trust (A1), as in the 11 November row below. And requests sent with no proxy at all also got answers from containers on the machine's network (A2, A5; A1 in the one holding the proxy's certificate): the local proxy is not the machine's only way out. Which part of the cloud network answered or refused those direct requests is inferred, not shown. Measured on 11 November: a container that shares the machine's network, is told about the proxy, and is given the proxy's certificate can reach the npm registry, the Python package index and the Anthropic API. That was a test container started for this check; the builder's own project containers are not all set up that way (item 2 of "What this means for Stage 1" says which part gets what). The table rows below are the 11 November measurements, unchanged.
- **How much memory and disk?** 4 processor cores, 15 GiB of memory (14 GiB free), 30 GB of writable disk at session start.
- **Anything else?** Docker Hub, the public image library, refused one download with a "too many requests" error and accepted it on retry a minute later. Images should be pinned and, on the demo server, pulled with an account or from a mirror.

## What this means for Stage 1

1. Development and the automated test harness can run here. Each session must start the Docker daemon first.
2. In a cloud session, project containers must share the machine's network and use the session proxy with its certificate. *Corrected by measurement on 12 November 2026 (package 0.6a, `evidence/2026-11-12-package-0.6a/isolation-checks.md`): "must" rested on the reason in the first section, which does not hold as written, and the project's containers do not all use the session proxy and its certificate. In use on the development profile (read from the sandbox manager's Compose settings and the template's Dockerfile, and seen in the run for the app and tools containers): every project container except the engine shares the machine's network, and the engine container has none; the app image's build is given the session proxy as build arguments and a copy of its certificate in the build stage; the egress proxy container is given the session proxy and has the certificate mounted; the tools image holds a copy of the certificate from the build stage; the app and tools containers are given no proxy setting, and the app container holds no copy of the certificate (none at the two places the 0.6a probe looked; the Dockerfile's `run` stage copies none). Whether project containers could work off the machine's network was not tried (known gap 60); on it, a connection opened from the app and tools containers to every service listening on the machine.* This is a development-only arrangement. On a demo server there is no such proxy, and the design note (section 2.5) describes the egress proxy the builder runs for itself.
3. Nothing can be hosted here: the machine pauses when idle and running processes do not survive. The owner sees progress through screenshots and recordings in pull requests until a demo server exists.
4. Whether a web page served inside a session can be opened by the owner is tested at the end of this session: a one-page test server was started and its port was reported to the Claude app. The result is in `docs/STATUS.md`.

## Update, 12 and 13 November 2026: Docker start-up and the `vibe-build` environment

Measured in one cloud session on 12 and 13 November 2026, on one disk kept across three restarts (12 Nov 12:39; 13 Nov 02:47 and 05:55). The kernel build changed between the days (6.18.44-fc-v378 on 12 Nov, -v445 on 13 Nov), so whether it was the same machine is not known; only the disk is shown to have been kept.

- **`service docker start` failed on 12 November** (exit code 2, daemon not running). Docker's start script (`/etc/init.d/docker`) stops at the first error, and two of its lines try to raise system limits the session is not allowed to raise ("ulimit: error setting limit (Operation not permitted)"). On 11 November `service docker start` worked with "one harmless warning about a ulimit setting" (first section; the warning's text was not recorded); why it differs is not known.
- **Fix, run and checked:** adding `|| true` to the start script's three `ulimit` lines lets it carry on, so Docker runs without the raised limits (known gap 65). After it, `service docker start` returned 0 and containers ran from `postgres:16-alpine` (16.15), `node:22-alpine` (22.23.5) and `python:3.13-slim` (3.13.18).
- **The `vibe-build` cloud environment** (personal, created on 12 Nov with the owner's approval) carries a *setup script*: commands the cloud service runs as root before a session starts. As written, it applies the fix above, starts Docker, downloads those three images by tag, and stops Docker again. Every step is allowed to fail and the script always ends with success, so, as written, a failing step should not stop a session starting; a step that hangs instead of failing, such as a stalled download, has no time limit (read from the script, not seen; known gap 65). When it runs, per Anthropic's documentation (`docs/SOURCES.md`, 13 Nov): the first time a session starts in the environment; if it finishes within roughly five minutes, the disk it leaves, images included, is saved as a snapshot that later sessions start from without running the script (a longer run, such as one held up by a stalled download, is not saved); it runs again when the script or the allowed hosts change, and when the snapshot expires after roughly seven days; not when a session's machine is restored after being idle; and before the environment's variables are set.
- **Its network settings:** limited, package managers allowed. On 12 Nov and at about 03:35 on 13 Nov it had the same twenty allowed hosts as "Default". Nineteen of the twenty are the research sites the owner approved on 11 Nov (`docs/OPEN-DECISIONS.md`); the twentieth, `openrouter.ai`, is not on that list. It is on "vibe-build" because Claude Code's proposal to create the environment gave it the twenty hosts "Default" had that day, and the owner approved that card, which listed them (`docs/DECISIONS.md`, 12 Nov); how it came to be on "Default" was not looked into (`docs/STATUS.md`, Money). At 06:30 on 13 Nov "vibe-build" had twenty-three: those twenty plus `www.google.com`, `policies.google.com` and `developer.chrome.com`, while "Default" still had twenty. These are among the addresses the session's proxy refused on 13 Nov while Google's terms were sought for question 11 (`docs/SOURCES.md`); that this was the reason they were added is assumed, not checked, and who added them, and when, is not recorded here. A change to the allowed hosts is the owner's (plan section 4). Per the documentation, it also makes the setup script run again for the next new session, so that session's images come from a new download by tag (`docs/STATUS.md`, question 11).
- **Its variables:** none, and no secrets, when created. By the afternoon of 12 Nov a variable named `VIBEBUILD_KEY` had been added. On 13 Nov the environment tool gave no list of names for "vibe-build" (`null`, where at creation it gave an empty list). The session running on it was still given a variable named `VIBEBUILD_KEY`, not empty, after its machine restarted at 02:47, and was not given one after the restart at 05:55; both checks looked at the name and at whether the value was empty, never at the value. A session reads the environment's variables again each time its machine is restored (`docs/SOURCES.md`, 13 Nov), so the entry was probably removed between those two times; this was not checked in the environment menu (`docs/STATUS.md`, question 2).
- **Run by hand:** on 12 Nov, in the session that made the environment, the script ran twice by hand, about 15 seconds the first time and 5 the second.
- **Not shown:** the script running by itself. The session that made the environment was moved onto it after that session had started, so no session start of its own ran the script. Whether other sessions started on "vibe-build" ran it, and when, is not known here. The images a session finds come from whichever run built its snapshot, so the same tag can name different images in different sessions (`docs/STATUS.md`, question 11).
- **Seen on 13 November 2026:** the disk was kept across restarts on 12 Nov at 12:39 and on 13 Nov at 02:47 and 05:55. The start script is still dated 12 Nov 07:02 (the setup script's first step rewrites that file each time it runs, which would have given it a new date), and Docker's log (`/var/log/docker.log`) has no entry between 12 Nov 12:41 and that session's own start attempt on 13 Nov at 02:53, nor after its test run ended at 03:43 until it started Docker again. So the setup script did not run at any of the three restarts, as the documentation leads one to expect for a machine restored after being idle; the patch and the three images present since then come from the hand run of 12 Nov. After the 12:39 restart `service docker start` returned 0 and `postgres:16-alpine` ran.
- **A second way Docker fails to start here, seen on 13 November 2026:** after the 02:47 restart, `service docker start` printed "done" and returned, but the daemon stopped at once. Its log: "failed to start daemon, ensure docker is not running or delete /var/run/docker.pid: process with PID 343 is still running". The file `/var/run/docker.pid` was left from the daemon started on 12 Nov at 12:40, because `/run` is on the kept disk here, not cleared at restart. Docker's own check reports that some process had number 343 at that moment; that it was not Docker is inferred from the file dating from before the restart, and it had exited by the time it was looked for. With no `dockerd` running, deleting that file and running `service docker start` again started the daemon (Docker 29.9.2). After the 05:55 restart the same kind of file, from the 02:54 start, was there again with no `dockerd` running. The setup script does not handle this case, and `nohup dockerd` (the other start command in `CLAUDE.md`) uses the same file, so it would be expected to fail the same way (not tried). Known gap 65.
- **Images and the open licence question:** the setup script fetches its three images by tag. `node:22-alpine` and `postgres:16-alpine` are among the images the owner's question 11 asks about (`docs/STATUS.md`); `python:3.13-slim` is not named there and nothing in the builder uses it. On this disk, by hand, each of the three was run on 12 Nov at 07:02 to print its version, and `postgres:16-alpine` was run once more after the 12:39 restart; `python:3.13-slim` was not run again. `node:22-alpine` and `postgres:16-alpine` are also run by the builder's sandboxes, so the live tests in `npm test` ran them here on 12 Nov at 12:41 and again on 13 Nov before the merge (Docker's log, containers `builder_p_live-db-1` and `builder_p_live-egress-1` at 12:41 on 12 Nov; the digests run on 13 Nov are in `docs/STATUS.md`, question 11, and `docs/SOURCES.md`). The `node:22-alpine` here is `sha256:1314fb30ec37…`, not the image the licence inventory of 13 Nov read.
