# Environment check (Task 0, item 1)

Measured on 11 November 2026 inside a Claude Code cloud session. Everything here was run, not assumed. Re-run before relying on it: the documentation says these resources are approximate and may change.

## Plain-language result

- **Can it run a container?** Yes. The Docker daemon is not running when a session starts; it starts with one command and then works. *Not always, as seen on 12 and 13 November 2026: on 12 Nov that command failed until Docker's start script was patched, and on 13 Nov it failed until a file left from an earlier start was deleted (section "Update, 12 and 13 November 2026").*
- **Can a container reach the package registry?** Yes, with a workaround. As first written on 11 November: "On Docker's default network a container has no internet at all, because this machine reaches the internet only through a local proxy that listens on the machine itself." *Corrected by measurement on 12 November 2026 (package 0.6a, `evidence/2026-11-12-package-0.6a/isolation-checks.md`): neither half holds as written.* A container on Docker's default network, with no proxy setting and no certificate, got answers on port 80 (A2, A5) and to name lookups (D1, D5); its HTTPS request to the registry got a certificate it did not trust (A1), as in the 11 November row below. And requests sent with no proxy at all also got answers from containers on the machine's network (A2, A5; A1 in the one holding the proxy's certificate): the local proxy is not the machine's only way out. Which part of the cloud network answered or refused those direct requests is inferred, not shown. Measured on 11 November: a container that shares the machine's network, is told about the proxy, and is given the proxy's certificate can reach the npm registry, the Python package index and the Anthropic API. That was a test container started for this check; the builder's own project containers are not all set up that way (item 2 of "What this means for Stage 1" says which part gets what). The table rows below are the 11 November measurements, unchanged.
- **How much memory and disk?** 4 processor cores, 15 GiB of memory (14 GiB free), 30 GB of writable disk at session start.
- **Anything else?** Docker Hub, the public image library, refused one download with a "too many requests" error and accepted it on retry a minute later. Images should be pinned and, on the demo server, pulled with an account or from a mirror.

## What this means for Stage 1

1. Development and the automated test harness can run here. Each session must start the Docker daemon first.
2. In a cloud session, project containers must share the machine's network and use the session proxy with its certificate. *Corrected by measurement on 12 November 2026 (package 0.6a, `evidence/2026-11-12-package-0.6a/isolation-checks.md`): "must" rested on the reason in the first section, which does not hold as written, and the project's containers do not all use the session proxy and its certificate. In use on the development profile (read from the sandbox manager's Compose settings and the template's Dockerfile, and seen in the run for the app and tools containers): every project container except the engine shares the machine's network, and the engine container has none; the app image's build is given the session proxy as build arguments and a copy of its certificate in the build stage; the egress proxy container is given the session proxy and has the certificate mounted; the tools image holds a copy of the certificate from the build stage; the app and tools containers are given no proxy setting, and the app container holds no copy of the certificate (none at the two places the 0.6a probe looked; the Dockerfile's `run` stage copies none). Whether project containers could work off the machine's network was not tried (known gap 60); on it, a connection opened from the app and tools containers to every service listening on the machine.* This is a development-only arrangement. On a demo server there is no such proxy, and the design note (section 2.5) describes the egress proxy the builder runs for itself.
3. Nothing can be hosted here: the machine pauses when idle and running processes do not survive. The owner sees progress through screenshots and recordings in pull requests until a demo server exists.
4. Whether a web page served inside a session can be opened by the owner is tested at the end of this session: a one-page test server was started and its port was reported to the Claude app. The result is in `docs/STATUS.md`.

## Update, 12 and 13 November 2026: Docker start-up and the `vibe-build` environment

*Added with pull request #8.* Measured in one cloud session on 12 and 13 November 2026, on one disk kept across three restarts (12 Nov 12:39; 13 Nov 02:47 and 05:55). The kernel build changed between the days (6.18.44-fc-v378 on 12 Nov, -v445 on 13 Nov), so whether it was the same machine is not known; only the disk is shown to have been kept.

- **`service docker start` failed on 12 November** (exit code 2, daemon not running). Docker's start script (`/etc/init.d/docker`) stops at the first error, and two of its lines try to raise system limits the session is not allowed to raise ("ulimit: error setting limit (Operation not permitted)"). On 11 November `service docker start` worked with "one harmless warning about a ulimit setting" (first section; the warning's text was not recorded); why it differs is not known.
- **Fix, run and checked:** adding `|| true` to the start script's three `ulimit` lines lets it carry on, so Docker runs without the raised limits (known gap 67). After it, `service docker start` returned 0 and containers ran from `postgres:16-alpine` (16.15), `node:22-alpine` (22.23.5) and `python:3.13-slim` (3.13.18).
- **The `vibe-build` cloud environment** (personal, created on 12 Nov with the owner's approval) carries a *setup script*: commands the cloud service runs as root before a session starts. As written, it applies the fix above, starts Docker, downloads those three images by tag, and stops Docker again. Every step is allowed to fail and the script always ends with success, so, as written, a failing step should not stop a session starting; a step that hangs instead of failing, such as a stalled download, has no time limit (read from the script, not seen; known gap 67). When it runs, per Anthropic's documentation (`docs/SOURCES.md`, 13 Nov): the first time a session starts in the environment; if it finishes within roughly five minutes, the disk it leaves, images included, is saved as a snapshot that later sessions start from without running the script (a longer run, such as one held up by a stalled download, is not saved); it runs again when the script or the allowed hosts change, and when the snapshot expires after roughly seven days; not when a session's machine is restored after being idle; and before the environment's variables are set. A session re-reads the environment's variables each time its machine is restored, or rebuilt after being reclaimed.

## Session set-up

*Added 13 Nov 2026 by package 3.1b (the third outside review supplied by the owner, item 3).* What a cloud session does before it runs the checks. Since package 3.1b, `npm test` fails, by design, when Docker does not answer or the approved browser zip is not in the folder `BUILDER_BROWSER_CACHE` names: the live acceptance tests then fail with a message that names what is missing and how to put it right. They are never skipped.

1. **Start Docker:** `service docker start`. If it stops at a `ulimit` line, or the daemon does not stay running, follow `CLAUDE.md`, Commands, and the section above (the `ulimit` patch; `nohup dockerd > /tmp/dockerd.log 2>&1 &`; a `docker.pid` file left from before a restart).
2. **Start PostgreSQL:** `service postgresql start`, then, inside `builder/`, `bash scripts/dev-db.sh`.
3. **Fetch the browser:** inside `builder/`, run `BUILDER_BROWSER_CACHE=<a folder outside the repository> npx tsx scripts/fetch-browser.ts`, and keep `BUILDER_BROWSER_CACHE` set to that folder for `npm test`. The script downloads about 120 MB (119,809,080 bytes) from the one address recorded in `docs/SOURCES.md` and `builder/src/acceptance/runner-image.ts`, through the session's proxy, and puts the zip in place only if its size and SHA-256 are the approved ones. It never replaces a file already there; run again when the approved zip is there, it downloads nothing. Exit code 0 means the approved zip is in place.
   - **If it is refused** (for example "The proxy at … refused the tunnel to storage.googleapis.com:443: it answered 403", or a network error): this session cannot fetch the browser, so it cannot exercise the browser, and `npm test` fails. Do not copy a zip from elsewhere into the folder; nothing else is accepted. Tell the owner: his cloud environment must let `storage.googleapis.com` through (a change he approves on a card); a new session then runs this step again (known gap 110). Until then, say plainly that the browser was not exercised.
   - **What the session's network answered on 13 Nov 2026:** 200 at 10:09 UTC through the session's proxy, the whole zip fetched and checked; 200 to a `HEAD` request at 10:45, after the machine's container was restarted (`docs/SOURCES.md`, package 3.1b). Earlier that day the host had been recorded as not let through. A new session's network may differ.
   - The first live run after the zip is fetched builds the runner image from it, which downloads Ubuntu and npm packages (package 3.1); later runs use Docker's cache of that build while it is kept.
4. **Then the checks**, inside `builder/`: `npm run typecheck`, `npm test`, `npm run check:licences`.
